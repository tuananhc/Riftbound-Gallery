# Monday 12 October 2026 - Dev Log No. 12

Walked through the one-time AWS setup that lets GitHub Actions deploy the
Lambdas without stored credentials, covering where the OIDC identity provider
lives in IAM and how the deploy role is scoped to this repo and branch. Also
fixed the legend picker being clipped on the last rows of the match history.

---

## Decisions Made

- **GitHub authenticates to AWS with OIDC, not access keys.**
  An IAM OIDC identity provider trusts GitHub's token issuer, and the workflow
  assumes a role with a short-lived token. Nothing long-lived is stored in the
  repo, so there are no keys to rotate or leak. This is what
  `.github/workflows/README.md` step 1 sets up.

- **Create the deploy role via the "Web identity" flow rather than "Custom
  trust policy".**
  Both produce the same trust policy; the Web identity screen builds the JSON
  from the org / repo / branch fields, which avoids hand-editing the account ID
  and `sub` string. The caveat recorded for later: the branch field must be
  filled in, otherwise the console writes `repo:tuananhc/Riftbound-Gallery:*`
  and any branch or pull request in the repo could assume the role. Pasting the
  README's `trust-policy.json` under Custom trust policy stays a valid
  alternative for anyone who prefers the explicit document.

- **Deploy permissions go in an inline policy on the role.**
  `deploy-policy.json` only grants `UpdateFunctionCode` / `GetFunction` /
  `GetFunctionConfiguration` / `PublishVersion` on the three named functions.
  Inline keeps it bound to this one role (matching `put-role-policy` in the
  README) rather than creating a managed policy that could be attached
  elsewhere by accident.

- **The legend picker flips above the row instead of being capped.**
  Opening upward keeps the full 360px list usable on the last rows; capping the
  height to the space below would have made the bottom rows show a much shorter
  list than the rest. Direction is measured per click rather than tracked in a
  resize listener, since the only moment it matters is when the menu opens.

## Topics Discussed

- **Where "register GitHub as a login provider" happens in AWS** — IAM →
  Identity providers → Add provider → OpenID Connect. IAM is global, so no
  region applies, and the provider is created once per account.
- **Provider URL vs repository URL** — the provider URL is always
  `https://token.actions.githubusercontent.com` (GitHub's token issuer, the
  same for every repo). The repository only appears later, in the trust
  policy's `sub` condition as
  `repo:tuananhc/Riftbound-Gallery:ref:refs/heads/master` — a claim string, not
  a URL.
- **Checking for an existing provider** — `aws iam
  list-open-id-connect-providers`; `create-open-id-connect-provider` returning
  `EntityAlreadyExists` is harmless. `aws sts get-caller-identity` gives the
  account ID needed for the ARNs, and `git remote -v` confirms the owner/repo
  in the trust policy matches the actual remote.
- **What the deploy role deliberately cannot do** — no DynamoDB, no Cognito, no
  function creation. The functions' own execution roles hold the table
  permissions and are untouched by CI.
- **Legend picker clipping** — how to decide the open direction from
  `window.innerHeight - rect.bottom` versus `rect.top`.

---

## Decisions Made

- **Theme mimics zero.gg's structure, not its palette.**
  Took their flat surfaces (`#121212` page / `#1a1a1a` card / `#333` hairline
  borders), square corners and monospace type, but replaced the amber accent
  with a cool grey-blue (`#8fa3bf`). Emphasis now comes from brightness rather
  than hue; the old warm-cream-on-navy scheme is gone.

- **Theme applied site-wide through the tokens, not page by page.**
  `COLORS` in `src/lib/data.js` was rewritten and every hardcoded hex in
  `src/components` and `src/app` mapped onto the new palette in one pass, so
  cards, news, navbar, auth and profile shift together. Restyling only the
  profile page would have left the site looking like two products.

- **`COLORS.gold` renamed to `COLORS.accent`.**
  The token is no longer gold, and a name describing the colour rather than the
  role would have gone stale again at the next theme change. Added
  `bgRaised` / `bgHover` / `accentGlow` for surfaces that components were
  hardcoding, plus semantic `win` / `loss` / `draw`.

- **Rune and rarity colours are exempt from the theme.**
  `src/lib/cards/data.js` colours encode game information (domains, rarity), so
  greying them would destroy meaning. Card art is likewise untouched.

- **UI typography switched to monospace (`FONT_MONO`, Geist Mono).**
  Matches the reference and replaces 118 copies of the `'Segoe UI'` literal
  with one imported token. CLAUDE.md's Cinzel / Crimson Pro rule was dropped
  because no component actually used those fonts — the documented rule and the
  code had diverged.

- **Champion icons are derived from `tags_text`, with punctuation stripped.**
  S3 filenames turned out to be the champion name minus whitespace and
  punctuation (`Kai'Sa` → `KaiSa.png`, `Lee Sin` → `LeeSin.png`). An earlier
  upload used the full name with spaces; the helper now targets the stripped
  form. Rows fall back to the card art when an icon 404s rather than showing a
  gap, since the bucket isn't complete.

- **Legends are fetched server-side and passed as a prop.**
  They were read from the `CardStoreProvider` context, which only the Cards page
  populates — hence the "Visit the Cards page first" prompt on a cold load of
  the profile. The root page is now an async server component calling
  `getLegends()`, matching the project rule that server components fetch and
  client components render. Shared `isBaseCard` / `legendOptions` moved into
  `src/lib/cards/data.js` instead of being copied into components.

# Monday 12 October 2026 - Dev Log No. 12 (continued, part 3)

Took the backend from hand-built AWS resources to CloudFormation deployed by
GitHub Actions on every push to master. Along the way fixed the Lambda deploy
workflow's configuration errors and Vercel's "Region is missing" build failure,
inventoried the live AWS account through CloudShell, and worked through the
first bootstrap attempts.

---

## Decisions Made

- **All backend resources are defined in CloudFormation (`infra/backend.yml`)
  and deployed on every push to master.**
  The manual setup — functions, roles, routes, authorizer, CORS, permissions,
  each a separate CLI command — kept producing config errors (wrong function
  names, missing variables, missing functions). A template makes the setup
  reproducible and reviewable, and every push converges AWS to the repo. Plain
  CloudFormation was chosen over SAM/CDK so the only tooling is the AWS CLI
  already on the runner.

- **The Cognito pool, `Users` and `RiftboundCards` are referenced, not owned.**
  They hold real data. The pool's email-as-alias setting and SPA no-secret
  client are fixed at creation, so CloudFormation must never be in a position
  to replace it. `Users` is referenced by name, with a `CreateUsersTable`
  parameter for fresh accounts. CloudFormation import was considered and
  rejected: properties must match the live resource exactly, and a later
  mismatch on an immutable property would trigger a replacement.

- **The stack creates its own functions (`riftbound-*`) rather than adopting the
  hand-made `sync-users-to-dynamodb`.** Avoids name collisions and an import;
  the cost is a one-time re-point of the Cognito Post-confirmation trigger.

- **Two-role CI design.** GitHub's OIDC role (`github-deploy-riftbound`) can only
  create change sets on the `riftbound` stack, pass the execution role to
  CloudFormation, and upload code. The broad create/delete permissions sit on
  `riftbound-cfn-exec`, which only CloudFormation can assume, scoped to
  `riftbound-fn-*` roles, `riftbound-*` functions and log groups, and the two
  table names. A leaked GitHub token can't create resources directly.

- **CI's own permissions live in a hand-deployed bootstrap stack
  (`infra/bootstrap.yml`).** CI can't safely grant itself permissions, so the
  deploy role, execution role and artifacts bucket are deployed once by hand.
  The GitHub OIDC provider is account-wide, so it is referenced, not owned.

- **The deploy role keeps its existing name.** The bootstrap recreates
  `github-deploy-riftbound` after the hand-made one is deleted, so the
  `AWS_DEPLOY_ROLE` repo variable stays valid without another GitHub settings
  change.

- **Lambda code is one content-addressed zip.** `deploy.sh` hashes the
  `lambda/*.mjs` sources and uploads `lambda/<hash>.zip` only if new. Pushes
  that don't touch `lambda/` then produce no code change and an empty change
  set. This sidesteps `aws cloudformation package`, whose zips embed file
  timestamps and would redeploy all three functions on every run.

- **Every parameter is passed explicitly in `deploy.sh`.**
  `aws cloudformation deploy` otherwise keeps a parameter's previous value, so
  editing a template default would silently do nothing. Environment values
  (pool IDs, table names, origins) live at the top of `deploy.sh`.

- **Tables use `DeletionPolicy: RetainExceptOnCreate`**, kept on stack deletion
  but cleaned up if the first create rolls back, so an orphan can't block the
  retry. DynamoDB deletion protection was left off because it would make that
  rollback fail.

- **CORS allows any origin (`*`).** Every route requires a Cognito ID token in
  the `Authorization` header, which another site can't read, and no cookies are
  used — so a wildcard doesn't weaken anything, and production can't break on
  an unlisted domain. Overridable via `ALLOWED_ORIGINS` in `deploy.sh`.

- **Runtime `nodejs24.x` on arm64**, matching what the account already runs
  (`sync-users-to-dynamodb`) and clearing the AWS SDK's Node ≥ 22 warning.

- **Vercel reads `RIFTBOUND_AWS_*` env names.** Vercel reserves `AWS_*` for its
  own runtime, so `src/lib/db.js` reads the prefixed names first and falls back
  to `AWS_*` locally, defaulting the region to `ap-southeast-2`.

- **The repo is the source of truth for function names, using kebab-case**
  (briefly `save-match-history` / `user-profile` / `sync-users-to-dynamodb`
  before CloudFormation took over and they became `riftbound-*`).
