# Saturday 30 May 2026 - Dev Log No. 7

Introduced a global card store via React Context so cards fetched on the `/cards` page are shared across routes without re-fetching, added a cards page loading skeleton that fires on hard load, and worked through the layout-vs-page fetch placement trade-off.

---

## Decisions Made

- **Fetch cards in `page.js`, populate context via `useEffect` — not in `layout.js`**
  The initial approach fetched cards in `layout.js` and passed them to `CardStoreProvider`. This blocked the layout from rendering until the fetch resolved, which meant `loading.js` (the Suspense fallback) never showed on hard load. Moved the fetch back to `page.js` so Next.js wraps it in a Suspense boundary, allowing `loading.js` to render immediately. `CardGrid` calls `useSetCards()` in a `useEffect` after mount to populate the context for subsequent cross-route navigation.

- **Context provider starts empty, seeded by `CardGrid` on mount**
  `CardStoreProvider` initialises with an empty array. When the user visits `/` (cards page), `CardGrid` fires `setCards(initialCards)` once after hydration. Any subsequent navigation to `/decks` finds the context populated — `DeckSources` calls `useCards()` and computes legends from it. If a user navigates directly to `/decks` without visiting `/` first, the context is empty and the legend filter shows its "no legends" placeholder, which is acceptable.

- **`useEffect` deps: `[initialCards, setCards]`**
  Both are stable references — `setCards` is a `useState` setter (never changes), and `initialCards` comes from ISR (same array reference per cached render). Including them satisfies the exhaustive-deps lint rule without causing extra runs.

- **`revalidate` moved back to `page.js`**
  Since the fetch is in `page.js`, the ISR revalidation period belongs there. The layout is now sync and has no `revalidate` export.

- **Loading skeleton mirrors real layout exactly**
  Skeleton uses the same 240px sidebar width, same `minmax(200px, 1fr)` grid, same 744/1039 card aspect ratio, and a shimmer opacity-pulse animation via a single CSS class. Rendering it as a server component in `loading.js` means it has no JS overhead and renders instantly.

## Topics Discussed

- **Next.js Suspense / `loading.js`** — Next.js App Router uses native React Suspense. `loading.js` automatically wraps `page.js` in a `<Suspense>` boundary. Manual `<Suspense>` can wrap individual async server components for finer-grained streaming within a page.
- **Why `loading.js` didn't fire with layout fetch** — `loading.js` wraps `{children}` (the page), not the layout. An async layout blocks before the Suspense boundary is reached, so the fallback never renders. Fetch must be in the page for the skeleton to appear.
- **`cache()` from React vs `unstable_cache`** — discussed `cache()` as a per-request deduplication mechanism (not persistent cache). Would allow both layout and page to call `getAllCards()` without a double DynamoDB hit within the same render, but the chosen approach (page-only fetch + context seeding) was simpler and avoided any cache-size concerns.
